# 先生URLに合う証明書の確認・再発行・復元（#40 / OPS-08）

接続先は先に [#38の選択手順](network-selection.md) で確定する。
[9月15日の現地結果](connection-field-results-2026-09-15.md)では、実Wi-Fi
`10.53.64.130` に対して証明書SANは `127.0.0.1` と `192.168.1.35` だった。
この不一致を修復する。下記のIPは例なので、必ず当日の起動表示の値へ置き換える。

## 起動時の判定

起動案内・先生情報API・診断・証明書CLIは同じ検証を使う。
接続先未確定なら検証も未確認。確定後にSANのIP、有効期間、秘密鍵の一致を確認する。
確認済みならSAN、有効期間、検証時刻、証明書SHA256を出力し、不要な再発行はしない。
別端末の発行元信頼・マイク・字幕は、証明書が正常でも未確認のままにする。

古いSAN・期限切れ・有効期間前・鍵不整合・欠損・形式不正は理由を表示する。
権限不足などの取得不能は未確認であり、正常ではない。
不整合・未確認時はHTTPS待受を開始せず、このPC用のlocalhost先生URLを表示する。
生徒用HTTPは継続する。期限が残り30日未満の場合も再発行を案内する。

## 再発行

1. 起動案内のIPと実Wi-Fiを照合し、起動ログの検証結果を控える。
   診断は同じ `--config` と `--advertise-ip` で実行する。
2. サーバーの起動ウィンドウで Ctrl+C を押して停止する。
   ファイル二つの交換は稼働中のTLSに反映されないため、停止・再起動が必要。
3. アプリのフォルダで次を実行する。カスタム設定では `config.yaml` を変更する。

```powershell
.venv\Scripts\python scripts\make_cert.py --config config.yaml --advertise-ip 10.53.64.130 --force
```

既存の証明書・鍵は、設定された証明書ディレクトリの `backups/<日時-ID>/` に一組で退避される。
`manifest.json` は両方の復元先とSHA256、元々欠けていたファイルを記録する。
退避先はコマンド出力に表示される。秘密鍵を含むためサーバーPC内で管理し、添付・共有しない。
Windowsでは元の証明書フォルダと同様にフォルダのアクセス権を適用する。

新しい一組は一時ディレクトリで生成・検証してから交換する。
通常の書込失敗時は旧状態へ戻す。退避・検証失敗時は旧状態を変更しない。
電源断などでは二ファイルの交換完了は保証できないため、停止したまま下の復元操作を行う。
並行実行防止用 `.certificate-operation.lock` が残った場合は、証明書CLIとサーバーが
終了していることを確認し、そのロックファイルだけを削除して復元する。

## 復元

サーバー停止中に、同じ設定ファイルと現在確定したIPを指定する。
`<退避先>` は生成時に表示されたディレクトリ。

```powershell
.venv\Scripts\python scripts\make_cert.py --config config.yaml --advertise-ip 10.53.64.130 --restore "<退避先>"
```

復元先またはSHA256が異なる、不完全な退避は拒否する。
復元前の現在の一組も別の退避先へ保存する。元々なかったファイルは復元時も欠損状態へ戻す。
古いSANや期限切れも当時のまま戻るので、復元成功はTLS正常の意味ではない。
表示された検証結果を確認し、必要なら接続先の設定も [元へ戻す](network-selection.md#元へ戻す)。

## 再起動と公開TLS入口の再確認

```powershell
.venv\Scripts\python -m server.main --config config.yaml --advertise-ip 10.53.64.130 --open-browser
```

別のターミナルで実行する。

```powershell
.venv\Scripts\python -m server.diagnostics --config config.yaml --advertise-ip 10.53.64.130 --json
```

`tls.certificate` と `tls.key_pair`、`tls.served_certificate`（設定ファイルと提供中証明書の
SHA256一致）、`tls.https_health`（公開IPのHTTPS `/healthz` が200かつ `status:ok`）を照合する。
旧証明書が提供され続ける場合は再起動・待受PIDを確認する。
診断のTLS接続は証明書比較用であり、端末の発行元信頼を証明しない。
`/healthz` の `ready:false` はモデル未準備であり、TLS失敗とは分ける。

## 対象ブラウザでの警告承認と再確認

対象はChromebook Chrome・iPhone Chrome。iPhone Braveは#37で担当者が省略を指定済みで、
今回も未実施として扱う。各端末は既存の社内Wi-Fiを使い、先生画面は同時に一つだけ開く。
以下は許可された社内サーバーの自己署名証明書警告への操作であり、別端末への証明書導入や
ポリシー変更は行わない。再発行後は再び警告が出ることがある。

| ブラウザ | 操作 |
|---|---|
| Chromebook Chrome | 起動に表示された `https://<IP>:<HTTPSポート>/healthz` を開く。プライバシー警告のIPと担当者の案内を照合し、文言・エラーコードを記録。「詳細設定」から表示された当該IPへのアクセスリンクを選ぶ。 |
| iPhone Chrome | 同じHTTPS URLをアドレスバーに入力する。警告文言を記録し、「詳細設定」がある場合は開いて当該IPへ進むリンクを選ぶ。版・管理状態で表示が異なるため、実際のラベルと承認の有無を記録する。 |

進むリンクがない・管理者に遮断される場合は、その段階で未解決と記録して担当者へ渡す。
隠し操作、証明書インストール、セキュリティ設定変更で回避しない。
Chromeには進める警告と進めない警告がある（[Chromiumの警告文言](https://chromium.googlesource.com/chromium/src/+/main/components/security_interstitials_strings.grdp)、
[Chrome公式の証明書エラー案内](https://support.google.com/chromebook/answer/95669?hl=ja)）。
対象実機の操作ラベルの再確認は現地担当者との作業で行う。

承認後、アドレスバーが同じHTTPSのIP・ポートで、`/healthz` に `status:ok` が表示されることを確認する。
続いて `/teacher` を開き、最終URL、ページ表示、WS接続をそれぞれ記録する。
**警告承認、HTTPS疎通、マイク入力、字幕配信は別々の判定。** マイク入力・字幕は#41以降で確認する。

## 現地記録と引き継ぎ

開発PCでは2026年9月16日21:50 JST、実Wi-Fi IP `192.168.1.6` と一時ポート65302で
生成・通常起動し、公開IPのHTTPS `/healthz` が200かつ `status:ok`、提供中証明書SHA256が
生成ファイルと一致することを確認した。ループバックと同IPのHTTPS `/teacher` も200だった。
先生ページの取得では、一時証明書を当該検証プロセスだけで信頼してSANも照合した。
音声・翻訳はフェイク、一時証明書・設定を使用し、既存の証明書やOSの信頼ストアは変更していない。
一時サーバーは終了済み。これは社内端末の警告承認・マイク・字幕の成功証拠ではない。

変更後の社内実端末での再確認は未実施・現地担当者待ち。
9月15日に確認した接続についてFWは遮断原因として非該当だったが、今回の条件では未確認。
