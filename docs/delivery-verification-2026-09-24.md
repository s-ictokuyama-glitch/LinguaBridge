# マイク入力から字幕受信までの現地外検証（Issue #41）

2026-09-24、開発用Windows PCで実施。現地Wi-Fi・対象端末・実マイクは使っていない。
本書は**現地外の自動試験と手元環境での確認の証拠**である。社内Wi-Fiでの配信、対象端末の先生・生徒操作、
実マイクからの字幕受信の証拠ではない。現地確認は #43 F5・F8 で行う。

仕様: https://github.com/s-ictokuyama-glitch/LinguaBridge/issues/41
照合開始時のHEADは `73a1dd4`。本書と追加した試験は、本書を追加したコミットに含まれる。本番コードの変更なし。

## 今回追加した試験

### `tests/integration/test_live_delivery.py`

#42 の `Launcher` を共用する。本番の `server.main._serve` を、ループバック・空きポートで起動する。
Uvicorn・TLS・実TCP・本番のイベントループは実物で、推論だけフェイクにした。

- `test_pages_handshake_join_and_three_captions_are_separately_confirmed`
  1. ページ取得: 生徒ページ `/` をHTTPで、先生ページ `/teacher` をHTTPS（一時証明書で検証）で取得する。
  2. WS handshake: 先生は `wss://…:<HTTPS>/ws` へ、生徒2人は `ws://…:<HTTP>/ws` へ、それぞれページ自身のOriginで接続する。
  3. 参加: 先生1人、生徒2人（英語・中国語）が参加する。
  4. 配信: 配信を開始し、3発話を送る。各発話について次を確認する。
     - 先生に日本語の確定結果が届くこと
     - 各生徒には自分が選んだ言語の字幕だけが seq 1〜3 の順に届くこと
  - 終了通知までに余分な字幕（他言語・重複）が届かないことを確認する。
  - 終了後にクライアントが解放されることを確認する。送信キュー・待受・タスクの解放とイベントループの未処理例外は、共用する `Launcher.serving` の終了処理が確認する。
  - 段階ごとの結果は `record_property("stages")` として残す。
  - 先生情報API（参加コード・案内URL）はこの試験では確認しない。ループバックを公開IPにしない仕様のため、実Wi-Fi相当の接続先で `test_network_advertising.py`（#38）が確認している。
- `test_origin_rule_allows_and_rejects_on_both_production_listeners`: HTTP・HTTPSの両待受で次を確認する。
  - 許可: ページ自身のOrigin、Originなし（`replay_client` 等の非ブラウザ）、同じホストの別ポートのページ（ホストで照合する既存方針 #25 A-4）。許可した接続は参加まで成功する。
  - 拒否: 外部サイト、LAN内の別ホスト、`null`（file://・サンドボックス）、`127.0.0.1.unrelated.invalid` のような前方一致。拒否した接続は handshake の段階で403になり、拒否ごとに警告ログが1件出る。

### `tests/unit/test_page_ws_url.py`

`web/teacher.js`・`web/student.js` をNode.jsのvmで読み込み、`connect` が作るWebSocketのURLだけを観測する。

次の3条件で、両ページとも開いたページと同じホスト・ポートへ接続することを確認する。

| 開いたページ | 接続先 |
|---|---|
| `https:` `10.53.64.130:8443` | `wss://10.53.64.130:8443/ws` |
| `http:` `10.53.64.130:8000` | `ws://10.53.64.130:8000/ws` |
| `http:` `127.0.0.1:8000` | `ws://127.0.0.1:8000/ws` |

サーバー側のOrigin防御は、ページが自身のOriginで同じ待受へ接続することを前提にしている。この前提をこの試験で固定する。

## 試験が不具合を検出できることの確認

本番コードを1か所ずつ一時的に壊し、追加した試験を実行した。コードレビューの指摘で、初回の `student.js` の変異は試験のスタブに `hostname` がなく、ポートの検出ではない理由で失敗していたと分かった。スタブに `hostname`・`port` を加えてやり直した結果を載せる。各回の後に `git checkout` で元へ戻し、作業ツリーに差分がないことを確認した。

| 破壊 | 結果 |
|---|---|
| `origin_allowed` が常に許可を返す | Origin試験が失敗（拒否すべき接続が通る） |
| Originのホスト照合を完全一致から前方一致に変更 | Origin試験が失敗（`127.0.0.1.unrelated.invalid` が通る） |
| `broadcast_caption` が言語を見ずに全生徒へ送る | 配信試験が失敗（中国語の生徒に英語の字幕が届く） |
| `teacher.js` が常に `ws` で接続する | ページ試験のHTTPS先生ページが失敗 |
| `student.js` が接続先を `location.hostname` とポート8000に固定する | ページ試験のHTTPS（8443）の条件が失敗（8000の2条件は正しく成功） |
| Origin拒否時の警告ログを削除 | Origin試験が失敗（拒否1件ごとの警告が出ない） |

## 手元環境での確認

2026-09-24 00:44〜00:46 JST（UTCでは9月23日 15:44〜15:46。証明書の有効期間・検証時刻はUTCで出力される）、自宅Wi-Fi。NICの自動選択は `192.168.1.6`（物理NIC `Wi-Fi`）だった。
VMware・WSLの仮想NICは候補から除外された。

- 一時設定（HTTP 18700／HTTPS 18743）と一時証明書ディレクトリを使った。
- 証明書は `make_cert.py --config <一時設定> --advertise-ip 192.168.1.6` で生成した。
  - SAN: `127.0.0.1`・`192.168.1.6`
  - 検証: `ok`
  - SHA256: `8a6f6ae2…91a07f0f`
- 音声・翻訳は既定の実エンジンを使った。ASRは sherpa（`reazonspeech-k2-v2`）、翻訳は Hy-MT2（`Hy-MT2-1.8B-Q4_K_M`）。
- `python -B -m server.main --config <一時設定>` で起動した。
  - 起動画面の先生URLは `https://192.168.1.6:18743/teacher`、TLS証明書・鍵は `ok` だった。
  - 起動画面の生徒URLは `http://192.168.1.6:18700/?code=…` だった（参加コードは記録しない）。

クライアントは公開IP宛てに接続した。一時証明書は当該検証プロセスだけで信頼し、SAN照合を有効にした。
クライアントは使い捨てのスクリプトで、リポジトリには含めていない。手順はこの節のとおり（httpx でページ取得、websockets で先生 `wss`・生徒 `ws` を各ページのOriginで接続、参加、配信開始、録音を送信、字幕を収集）。
同じ段階の確認は、ループバックでは `test_live_delivery.py` で再現できる。

| 段階 | 時刻 | 結果 |
|---|---|---|
| ページ取得 | 00:45:24 | HTTP `/healthz`・`/`、HTTPS `/healthz`・`/teacher`・`/api/teacher-info` がすべて200。先生情報の先生URLは `https://192.168.1.6:18743/teacher`、参加URLは `http://192.168.1.6:18700/` |
| WS handshake | 00:45:24 | 先生は `wss://192.168.1.6:18743/ws`、生徒2人は `ws://192.168.1.6:18700/ws` へ、ページ自身のOriginで接続し、いずれも成立した。外部Origin（`https://unrelated.invalid`）は両待受で403 |
| 参加 | 00:45:24 | 先生、生徒（en・zh）が参加した |
| 配信 | 00:45:28〜00:45:42 | 下表。3発話 × 2言語の6件すべてを、各生徒が選んだ言語で受信した |

先生の音声には録音フィクスチャ `tests/fixtures/ja/01〜03.wav` を使った。100msずつ実時間で送り、各発話の後に2秒の無音を入れた。

| seq | 認識結果（ja） | en | zh | 遅延（en／zh） |
|---|---|---|---|---|
| 1 | 共和植物の光合成について勉強します | I will study the photosynthesis of共和 plants. | 学习共和植物的光合作用 | 468／718 ms |
| 2 | 光合成には日光と水と二酸化炭素が必要です | Photosynthesis requires sunlight, water, and carbon dioxide. | 光合作用需要阳光、水和二氧化碳。 | 594／954 ms |
| 3 | 教科書の四十二ページを開いてください | Please open page 42 of the textbook. | 请打开教科书的第四十二页。 | 500／890 ms |

- サーバーログのエラー・例外は0件。警告はOrigin拒否の2件だけだった。
- 終了後、コマンドラインが一時設定のものであることを照合してサーバーを停止し、待受0件を確認した。
- seq 1 は正解文「今日は植物の光合成について勉強します」の「今日は」が「共和」になった。
  - これはASRの認識精度の問題で、HTTP／WS・参加・配信の不具合ではない。
  - 認識精度の検証は実地検証（#19）の範囲であり、本issueでは修正しない。

### 限界

- クライアントはサーバーPC自身である。公開IP宛てでもOS内で折り返すので、Wi-Fi上の通信・別端末からの到達・FWの証拠ではない。別端末からの到達は、9月15日・18日に現地でページ・WS・参加まで確認済みで、配信は未確認。
- 先生の音声はWSへ直接送った。ブラウザのマイク権限、`getUserMedia`、AudioWorkletのリサンプリング、端末のマイク品質は通っていない。これらのブラウザ側の処理は、ヘッドレスのQA（`scripts/qa_browser.py`、制御したメディア）の範囲で、実マイクではない。

## #43への引き継ぎ

- **F5**（実マイクから字幕まで）
  1. サーバーPCで `start.bat` の起動画面から、先生URL（`https://<当日IP>:8443/teacher`）と生徒URL（`http://<当日IP>:8000/`）を控える。先生URLがHTTPSでなければ、先に #40 の手順（F4）で証明書を直す。
  2. Chromebook Chrome先生／iPhone Chrome生徒、次に役割を入れ替えた組合せで、順に次を行う。先生ページは同時に1つだけにする。
     1. 先生ページを開き、参加コード・QRが出ることを確認する。
     2. 生徒ページで言語（例: 英語）を選んで参加し、先生画面の人数が増えることを確認する。
     3. 先生が「開始」を押し、マイクを許可する。
     4. 短い日本語を3回話す（例: 「おはようございます」「教科書を開いてください」「今日は光合成を勉強します」）。
     5. 生徒が選んだ言語で、3発話それぞれの字幕が出ることを確認する。
  3. 段階ごとに成否と時刻を分けて記録する。
     - ページ取得、WS（先生画面の接続表示・人数）、参加、マイク許可、字幕（3件の受信と言語）
     - 発話内容・対象言語、端末・OS・ブラウザ版
  4. 期待結果: 手元では3発話 × 2言語の字幕が0.5〜1秒程度で届いた（録音入力・サーバーPC内の接続）。
     - 現地で失敗した場合は、その段階とサーバーログ（時刻・送信元）を控えて #41 へ返す。
     - 同じ操作を公開HTTP／WS境界の既存試験（`test_live_delivery.py`・`test_ws_boundary.py`）で再現してから修正する。
     - 修正後、同じ現地操作で再確認する。
  5. 不足する端末・証拠
     - 実マイク
     - Chromebook・iPhoneの実ブラウザでのマイク許可ダイアログ
     - 別端末間の字幕配信
     - 役割の入れ替え
     - Braveは #37 の合意済み省略（未実施、合格扱いしない）
- **F8**（最終報告）
  - 本書の手元確認は「自宅基本接続の回帰（サーバーPC内・録音入力）」として、各issueのローカル自動試験・社内実機試験とは分けて掲載する。
  - 現地で配信できない場合は、段階別の記録で判定する。経路・端末ポリシーによる実現不可は、証拠がある場合だけとする。
  - 単なる未確認を実現不可としない。
- **残課題**
  1. 対象端末の実マイクからの3発話と字幕受信（F5）。
  2. 役割を入れ替えた組合せ（F5）。
  3. 現地で不具合が見つかった場合の修正と再試験（#41へ返す）。
  4. ASRの誤認識は精度の検証（#19）で扱う。
