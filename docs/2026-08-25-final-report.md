## Architecture

先生1人の日本語音声を、同一LAN上の Windows ノートPC 1台（単一プロセス・単一 asyncio
イベントループ）で認識・翻訳し、生徒数十人のブラウザへ言語別に配信する。

```
先生ブラウザ ──WS(bin)──> ingest ─> VoiceSegmenter(Silero VAD)
                                        │
                                        ├─ Segment ──┐
                                        └─ TurnBoundary / InterimSegment
                                                     ↓
                                          asr_queue（秒数で有界・#25）
                                                     ↓
                                          ASRワーカー（1スレッド）
                                          sherpa-onnx + ReazonSpeech K2 v2
                                                     ↓
                                          TurnAssembler（文法境界で連結・#27）
                                                     ↓
                                          mt_queue（件数で有界・優先度つき・#25）
                                                     ↓
                                          MTワーカー（1スレッド）
                                          翻訳キャッシュ → Hy-MT2-1.8B (llama.cpp)
                                                     ↓
                                     生徒ごとの有界送信キュー（#25）→ 言語別配信
```

構造上の要点は3つ。

- **Segment と Turn を分けた**（#27・Parapper R-1）。`Segment` は ASR に投げる音声1単位、
  `Turn` は字幕カード1枚。文法境界の判定に ASR テキストが要るので、連結は VAD ではなく
  **ASR の後段**にある。
- **推論は各1スレッドに直列化**する。CTranslate2 / ONNX Runtime / llama.cpp が内部で
  マルチスレッド化するので、上でさらに並べても取り合うだけになる。
- **背圧は上流へ伝える**。ASR待ちは秒数で、MTは件数で、配信は生徒ごとに有界化されていて、
  どこも先生WSの受信ループをブロックしない（ブロックすると授業中に操作不能になる）。

### #32 の最終レビューで見つけて直したもの（2件とも実バグ）

1. **`_queued_audio_s` に浮動小数の端数が残る。** 積むのは到着順・引くのは処理順で
   足し引きの順序が違うため、2発話を続けて流すと全部さばいても 0 に戻らず `2.2e-16` が残る。
   残ると「ASR滞留は空か」を `> 0` で見ている2か所が**恒久的に「空でない」**と読む:
   - `_enqueue_interim` が interim を積まなくなる ＝ **partial字幕（#29）が例外もログも
     出さずに死ぬ**
   - `_enqueue_asr` の「キューが空なら長さによらず必ず受ける」carve-out が消え、
     `max_utterance_s`(30s) の強制分割が `asr_queue_seconds`(30s) に当たって捨てられうる

   1サンプル（62.5µs）より短い滞留は存在しないので、その下限で 0 に丸める。
   回帰テストは2本（滞留が厳密に 0 に戻ること／interim の門が再び開くこと）で、
   **修正を外すと両方赤くなることを確認済み**。

2. **`stats_snapshot()` がイベントループの外で `RuntimeError` を投げる。**
   `asyncio.all_tasks()` は走っているループが無いと例外になる。stats は
   決して例外を投げてはならないので、ループが無ければ 0 を返す。

## Hy-MT2 で最適化したもの

**モデルは Hy-MT2-1.8B Q4_K_M のまま**（map の絶対要件。クラウド翻訳への fallback も禁止）。
変えたのは**使い方**だけ（#26）。

| 項目 | before | after | 効果 |
|------|--------|-------|------|
| 発話をまたぐ翻訳キャッシュ | 無し | 有界LRU（`mt.cache_size: 512`） | 同一原文で推論しない |
| デコード | `temperature 0.7`（モデルカード推奨） | **貪欲**（`temperature 0.0`） | 品質差は測れず・遅延差なし・**出力が安定** |
| `max_tokens` | 固定 | 入力トークン数から算出（`max_tokens_cap: 512`） | 壊れた入力での暴走生成が入力長に見合った時間で止まる |
| CPUスレッド配分 | 未調整 | `mt.hy_mt2.threads: 4` / `asr.cpu_threads: 0` | 開発機では組合せを変えても合計が動かなかったので既定は据置 |

E2E（config だけ切り替えて背中合わせで計測）: **遅延中央値 2.43→2.12s（−13%）/
CPU中央値 164→117%**。

キャッシュの置き場所が要点で、**参照は推論スレッドへ渡す前**にある。エンジン側をラップ
してキャッシュすると、ヒットしても単一スレッドExecutorで実行中の推論（1件 570〜850ms）の
後ろに並んでしまい、「Hy-MT2 の前に置く」意味が消える。

**#26 の教訓（他のチケットに効いた）**: 往復翻訳CERはこの規模の差を判定できない。
訳文が完全一致した10項目でも往復CERが最大 27.6% ずれる ——
指標のノイズが判定したい差より大きいときは「差は測れない」が正しい答えになる。

### 長時間試験・MT負荷の上界（#32・**新規**）

`--mt-cache-size 0` で翻訳キャッシュを無効にした30分試験。
レポート: [`docs/accept/2026-08-25-acceptance-nocache.md`](accept/2026-08-25-acceptance-nocache.md)。

キャッシュ無効は「同じ文が二度と繰り返されない授業」＝**MT負荷の上界**にあたる。
実授業は既定（ヒット率 27.8%・#26 実測）とこの上界の間のどこかに入る。

| 指標 | 60分・キャッシュ既定 | 30分・キャッシュ無効 | 意味 |
|------|-------------------|-------------------|------|
| 翻訳キャッシュ ヒット率 | 92.8% | **0%** | 上界の条件 |
| Hy-MT2 実行回数 | 88回 / 60分 | **614回 / 30分** | 実効負荷は約 **14倍** |
| ASR 呼び出し | 698回 / 60分 | 348回 / 30分 | 音源が同じなので時間比どおり |
| **CPU 中央値** | 2.3% | **30.1%** | MT が動くとここが立つ |
| CPU p95 / 最大 | 55.3% / 550.1% | 477.6% / 589.0% | 論理16コア |
| 遅延 中央値 | 0.09s | **0.78s** | 基準 ≤5s に対してなお十分 |
| 遅延 p95 / 最大 | 0.51s / 1.83s | 1.64s / **1.84s** | 基準 ≤8s に対してなお十分 |
| 遅延ドリフト | 0.48→0.35s | 0.80→**0.90s**（+0.1s） | どちらも悪化判定に当たらない |
| メモリ 増分 / ピーク | +1MB / 2634MB | **−21MB** / 2652MB | リークなし |
| スレッド / ハンドル / タスク | 31→31 / 454→454 / 31→31 | 31→31 / 454→454 / 31→31 | 完全に同じ |
| ASR滞留 / MTキュー | 0→0 / 0→0 | 0→0 / 0→0 | 増加なし |
| 破棄 / 切断 / クラッシュ | 0 / 0 / 0 | 0 / 0 / 0 | — |
| 判定 | ✅ 合格 | ✅ 合格 | — |

**読み取り**: MT を14倍動かしても、崩れるのは CPU 中央値（2.3%→30.1%）と遅延中央値
（0.09s→0.78s）だけで、**リーク・キュー成長・破棄・ドリフトはどれも出ない**。
遅延は最悪でも 1.84s で、N-01 の最大 8s に対して 4倍以上の余裕がある。
つまり授業1コマぶんの MT 負荷は、この機械では**遅延の予算を使い切らない**。

ただし CPU 中央値 30.1% は**論理16コアでの値**で、1コアあたりに直すと約4.8コア相当。
学校実機（Core i5）の論理コア数によってはここが効く可能性がある ——
実機で最初に見るべき数値はこれになった。

### スケーリングベンチ（#32・**新規**）

`python scripts/scale_bench.py --minutes 2 --corpus ja_ext`（16点・点ごとにサーバーを立て直す）。
レポート: [`docs/bench/2026-08-25-scaling.md`](bench/2026-08-25-scaling.md)。

**ASR呼び出し回数** — 16点すべてで **19回**。生徒人数にも言語数にも依存しない。

| 生徒＼言語 | 1言語 | 2言語 | 3言語 | 5言語 |
|---------|------|------|------|------|
| 1名 | 19 | 19 | 19 | 19 |
| 10名 | 19 | 19 | 19 | 19 |
| 20名 | 19 | 19 | 19 | 19 |
| 40名 | 19 | 19 | 19 | 19 |

**MT呼び出し回数** — 行方向（生徒人数）で一定、列方向（言語数）にだけ比例する。

| 生徒＼言語 | 1言語 | 2言語 | 3言語 | 5言語 |
|---------|------|------|------|------|
| 1名 | 12 | 12 | 12 | 12 |
| 10名 | 12 | 24 | 36 | 60 |
| 20名 | 12 | 24 | 36 | 60 |
| 40名 | 12 | 24 | 36 | 60 |

12回 × 実効言語数がきれいに出ている。**生徒1名の行だけ全列 12 回**なのは異常ではなく、
生徒が言語へ順に割り当てられるため**生徒1名では何言語用意しても実効1言語**だから
（翻訳は選択者のいる言語にしか走らない）。この行は言語軸の主張には使えないので、
レポートの「読み取り」では比較から除外してある。

**40名 × 5言語でも** 破棄0・切断0・復元失敗0・クラッシュ0。

> **3言語・5言語の点は MT が `fake`**。実エンジン（Hy-MT2 / NLLB）の対応言語が
> `en` / `zh` の2つだけで、3言語以上では `_require_language_coverage` により
> **サーバーが起動しない**。多言語対応は未着手のイシュー #5 で、この map の
> destination の外にある。したがって言語軸で確かめられたのは**回数の主張だけ**で、
> 3/5言語列の遅延（0.11〜0.12s）は実エンジンの値ではない。
> 一方 **1言語・2言語は実 Hy-MT2** なので、「同一言語の人数で Hy-MT2 回数が増えない」
> というチケットの主張そのものは実エンジンで確認できている（12回 / 24回で不変）。

**副産物**: `tasks` は 13 / 31 / 51 / 91 と生徒数に比例して増える。これは
`asyncio.all_tasks()` が**生徒ごとのWSハンドラを含む**ためで、リークではない。
長時間試験でこの数字をリーク指標として読めるのは**接続数が一定のとき**だけ、
というレビュー中に出た指摘が数値で裏づけられた形になる。

## Privacy（外部通信ゼロをどう検証したか）

コードレビューではなく**機械判定**にしてある（#23）。

1. **ソケットガード**（`tests/net_guard.py`）— `socket.connect` / `connect_ex` /
   `sendto` / `create_connection` を包み、**宛先が決まる瞬間**にループバック・LAN 以外への
   接続が1件でもあればテストを落とす。`listen`/`accept` は包まない（LAN内で待ち受けるのが
   このアプリの仕事なので、受信は違反ではない）。
2. **ファイルガード**（`tests/fs_guard.py`）— 記録OFF時に音声ファイルが1バイトも
   書かれないこと、記録ON時に書かれるのが**復号可能なテキストだけ**であること
   （拡張子を偽装した音声を排除する）。
3. **`get_lan_ip()` から外向き UDP を排除した**（#23）。以前は `8.8.8.8` へ UDP connect して
   既定経路を調べていた（パケットは出ないが、宛先としては外部だった）。stdlib の
   インターフェース列挙に置き換えたので、ガードが**本当に**通るようになった。
4. **fail closed**。モデル未取得時はクラウドへ逃げずに `/ready` が 503 のままになる。
   Hy-MT2 が使えないときの代替翻訳経路は**実装として存在しない**。
5. 長時間試験（60分）中も外部への接続は発生していない（試験はガードの外だが、
   サーバーが使うのはローカルのモデルファイルと LAN の WebSocket だけで、
   上の1がその経路を CI で常時押さえている）。

## Remaining Risks

1. **学校実機（Core i5）で測っていない。** この報告の数値はすべて Ryzen 7 8840U の
   もので、楽観側に振れている。特に:
   - `monitoring.overload_audio_seconds`(10s) は #25 が whisper 構成の実測で置いた値。
     #28 で ASR のデコード固定費が 1.088s→0.027s（約40分の1）になり `audio_queue_seconds`
     の p95 が 0.00s になったので、**現在この閾値では過負荷を
     一度も検出できない**（#25 が直したはずの状態に戻っている）。実機で測り直して
     置き直す必要がある。60分試験でも過負荷サンプルは 0 だった。
   - `asr.cpu_threads: 0`（全論理コア）は開発機（16論理コア）での結論。論理コアが
     少ない実機では結論が変わりうる。
2. **CPU の余裕は MT の効き方で13倍変わる**。60分試験（キャッシュヒット 92.8%）で
   CPU中央値 2.3%、キャッシュ無効の30分試験（上界）で 30.1%。実授業はこの間に入る。
   遅延はどちらでも基準に余裕があるが、**実機の論理コア数が少ないとこの差が効く**。
3. **音源が合成音声（SAPI）。** CER の絶対値は実教室マイクの精度ではなく、
   エンジン間の相対比較にしか使えない。実授業の息継ぎ分布も SAPI とは違う
   （SAPI は読点で規則的に止まるが人間は止まらない）ので、partial の実効回数と
   `force_silence_ms`(1000ms) の待ちの代償は実地でしか決まらない（#19）。
4. **対応言語が en / zh の2つだけ。** 実エンジンの対応言語がそこまでなので、
   3言語・5言語では**サーバーが起動すらしない**（`_require_language_coverage`）。
   多言語対応は未着手のイシュー #5。
5. **表層分類器で埋まらない形が6件残っている** — 言い淀み3件（#27 の設計どおりの
   意図的な代償）・体言止め2件・「〜ように」1件。体言止めと「〜ように」は表層では
   原理的に区別できないので、実授業で頻出するなら形態素解析器が要る。頻度は #19 で見る。

## Next（次に価値の高い改善を最大3件）

1. **長時間試験で再接続経路を踏む**（切断注入）。60分試験でも30分試験でも
   **切断は1件も起きなかった**ので、再接続の差分復元と遅い生徒の隔離は
   長時間の実走では一度も踏まれていない（テストでは踏んでいる）。実授業で
   実際に起きるのは Wi-Fi 切断なので、ここは「テストは緑だが実走の証拠が無い」
   という状態のまま残っている。擬似生徒を試験中にランダムに切る仕組みを足せば、
   `reconnect_failures` と `send_queue_max` による隔離が長時間の実負荷で確かめられる。

2. **`monitoring.overload_audio_seconds` を指標ごと置き直す**（実機で）。
   #30 が `asr_wait_seconds`（純粋な待ち）と `asr_active_seconds`（処理中）を分けたので、
   「過負荷は待ちだけで判定すべきでは」が問える形になった。ただし #25 は
   「取り出した瞬間に 0 になると詰まっている最中だけ指標が消える」という理由で
   **意図的に**合算にしており、これは今も有効な反論。判定を待ちだけに寄せると
   閾値の意味そのものが変わるので、**指標と値を同時に決めること**。

3. **実地検証（#19）を回して fog を3つまとめて畳む。** 実授業の音声が1回取れれば、
   (a) partial を既定 ON にするか、(b) 教科用語 hotwords に何を入れるか、
   (c) 体言止めと「〜ように」が頻出するか（＝形態素解析器が要るか）が同時に決まる。
   どれも「実授業の分布を見ないと決められない」で止まっている項目で、
   個別に待つより1回の録音で3つ動く。
