# 判断ゲート②: ASRエンジンを日本語実測で決める（#28）

計測日 2026-08-24 / AMD Ryzen 7 8840U w/ Radeon 780M Graphics / 8コア16スレッド / RAM 16.4GB / Windows 11 / Python 3.12.10

再現: `python scripts/bench.py --phase asr-ext:reazon`（他フェーズは下表の見出しに記載）。
生データは [`2026-08-24-asr-gate.json`](2026-08-24-asr-gate.json)。

## 結論

**ReazonSpeech K2 v2 を既定にする**（`asr.engine: sherpa`）。

#24 が置いた合格線は2軸だった — 「small より速く、かつ CER が kotoba 側に寄っている」。
両方を、どちらも大差で満たした。

| 軸 | 合格線 | 実測 |
|----|--------|------|
| 精度 | CER が kotoba(3.94%) 側に寄る | **2.09%** — kotoba より良い |
| 速度 | whisper small(RTF 0.273) より速い | **RTF 0.026** — 10倍速い |

E2E（実サーバー・擬似生徒10名・2分リプレイ）でも全指標が改善した。**劣化した指標は無い**。

## 1. ASR 精度・速度（拡張コーパス ja_ext / 29クリップ・174.5秒）

`python scripts/bench.py --phase asr-ext:<構成>`。CER は NFKC正規化＋句読点除去後の文字単位。

| 構成 | CER | CER(句読点込み) | WER | RTF中央 | decode中央 | 固定費 a | 限界 b | ロード | peak RSS |
|------|-----|----------------|-----|---------|-----------|---------|--------|-------|---------|
| whisper small (旧既定) | 9.62% | 10.51% | 14.52% | 0.273 | 1.34s | 1.088s | 0.0472 | 0.7s | 375MB |
| kotoba-whisper-v2.0 | 3.94% | 6.19% | 6.85% | 1.02 | 4.91s | 4.717s | 0.0357 | 2.3s | 899MB |
| **ReazonSpeech (新既定)** | 2.09% | 6.42% | 5.75% | 0.026 | 0.13s | 0.027s | 0.0211 | 1.8s | 509MB |
| ReazonSpeech greedy | 3.48% | 7.74% | 9.04% | 0.021 | 0.11s | 0.025s | 0.0169 | 1.7s | 508MB |
| ReazonSpeech 全int8 | 3.94% | 8.30% | 9.04% | 0.021 | 0.11s | 0.024s | 0.0167 | 1.7s | 500MB |
| ReazonSpeech beam+hotwords | 2.09% | 6.42% | 5.75% | 0.027 | 0.14s | 0.027s | 0.0223 | 1.8s | 509MB |
| ReazonSpeech lead無し | 19.70% | 23.23% | 23.01% | 0.02 | 0.1s | 0.013s | 0.0172 | 1.7s | 505MB |

読み方:

- **固定費 a が 43分の1になる**（small 1.088s → 0.025s）。#24 が見つけた「ASR時間は固定費が
  支配的」という制約そのものが消えた。5秒発話の82%が固定費だったのが数%になる。
  これは #29（partial 字幕）の前提を変える — partial は固定費を繰り返し払う設計なので、
  small のままなら高くついたが、ReazonSpeech なら現実的になる。
- **CER 生（句読点込み）は kotoba に負ける**（6.42% vs 6.19%）。句読点を出さないぶんの
  当然の差で、採点から句読点を外した主指標では逆転する。表記仕様の差であって精度差ではない。
- **全int8 は採らない**。decoder を int8 にしても速度は変わらず CER だけ悪化する
  （3.48% → 3.94%、いずれも greedy）。既定は Parapper と同じ Int8Float32。
- **hotwords は既定では効かなかった**（29クリップ全てで beam と1文字も違わない）。
  機構が壊れているのではなく、直す対象が無かった — 別途 `原 子 の 数` を与えると
  「原子の風」→「原子の数」に直ることを確認済み（score=1.5 で十分）。

## 2. リードイン: 判定を左右した想定外の要因

**発話が音声の先頭からいきなり始まると encoder が冒頭を取りこぼす。**
先頭に無音を足すだけで CER が 19.70% → 3.48% に下がる（greedy・同一音源・同一モデル）。

| 先頭に足す無音 | CER |
|---------------|-----|
| 0ms | 19.70% |
| 300ms | 6.72% |
| 400ms | 5.79% |
| 500ms | 4.40% |
| 600ms | 3.48% ← 既定 |
| 700ms | 2.78% |
| 800ms | 3.24% |
| 1000ms | 3.36% |
| 1500ms | 2.67% |

具体例（`pause-02.wav`）:

```
lead   0ms: 下の方にある図を見てください
lead 600ms: 教科書の四十二ページの下の方にある図を見てください
```

600ms 付近からプラトーに入る。700ms(2.78%) や 1500ms(2.67%) の方が数値は良いが、
**29クリップの argmin は誤差**（800ms は 3.24% と逆に悪い）なので、曲線が平らになる
最小値として 600ms を採った。コストは decode 中央値 +0.01s しかない。

上流の `vad.pre_roll_ms`(240ms) では足りないので、**エンジン自身が足す**
（`server/asr/sherpa_engine.py`）。呼び出し側が pre_roll を持つかどうかに精度を依存させない。

**`dither` は 0.0 から動かしてはいけない。** kaldi の fbank 既定である 1.0 にすると
CER が 99.3% になる（このモデルは dither 無しで学習されている）。

この現象は #24 のベースライン計測では見えなかった。whisper 系は 30秒パディングを
するので同じ問題を持たず、**エンジンを替えたときだけ現れる種類の落とし穴**だった。
リードインを足さずに採点していれば CER 19.70% で「small より悪い」と誤って不採用にしていた。

## 3. 句読点の無い日本語を Hy-MT2 に入れる（#21 からの必須申し送り）

`python scripts/bench.py --phase mt-punct:hy-mt2`。

ReazonSpeech は句読点を出せない（#21: 語彙5,224に `。！？` が無い）。**ASR の CER が
下がっても訳文が崩れるなら採用できない**ので、これが採否の決定打だった。

実験は**入力の差を句読点だけに限定**した。実際の ASR 出力どうしを比べると誤認識の差が
混ざるので、正解テキストを「句読点あり」「句読点を抜いたもの」の2系統にして同じ文を2回翻訳する。
#26 B-5 の教訓により往復翻訳CERは使っていない（指標のノイズが判定したい差より大きい）。

15文 × 2言語 / temperature 0.0（貪欲）:

| 言語 | 訳文が完全一致 | 変化時の不一致中央値 |
|------|---------------|--------------------|
| en | 12/15 (80%) | 0.2211 |
| zh | 5/15 (33%) | 0.1193 |

**判定: 句読点なしでも Hy-MT2 は崩れない。**

- **出力側には句読点が付く。** 入力に `。` が無くても訳文は `。`/`.` で正しく区切られる。
  生徒が読む字幕の可読性は落ちない（#21 が懸念した項目のうち、これは杞憂だった）。
- 差は語彙選択のレベルで、**優劣は双方向**。むしろ句読点なしの方が良い例もある:

  | 入力 | 訳文 |
  |------|------|
  | 句読点あり | 下期我们将学习与呼吸不同的特点 |
  | 句読点なし | 下次我们将学习与呼吸的区别 ← こちらが原文に忠実 |

- 明確な劣化は1件だけ観測した（zh・「発表してもらいます」が `汇报`→`发布` になり敬体が薄れる）。
- 不一致率 100% の1件は `はい、えーと、それでは` — 内容語を持たない filler で、
  **句読点あり側の訳文も同程度に無意味**。品質差の証拠にはならない。
- 中国語の一致率が低い（33%）のは、中国語訳の方が語彙選択の自由度が高いため。
  英語は 80% 一致する。

**ただしこれは合成音声の整った文での結果**で、実授業の話し言葉では未検証。

## 4. 発話区切り: 句点が消えても `classifier: surface` は壊れなかった

`python scripts/bench.py --phase turn:morph:reazon`。

#21 は「ReazonSpeech を採るなら形態素解析器が必須になる」と申し送っていた。**これは外れた。**

| 構成 | カード | 不自然な分割 | ASR呼出 | MT呼出 | 平均字数 |
|------|-------|------------|--------|--------|---------|
| whisper small + morph（#27 既定） | 19 | 0 | 22 | 38 | 26.1 |
| ReazonSpeech + simple | 22 | 3 | 22 | 44 | 22.5 |
| **ReazonSpeech + morph（新既定）** | 19 | 0 | 22 | 38 | 26.1 |

**ReazonSpeech + morph は whisper + morph と1件も違わない**（19カード / 不自然な分割0 / MT呼出38）。

理由は Turn 確定の内訳を見ると分かる:

| エンジン | strong_end（句点） | predicate_end（〜です/〜ます） | flush |
|---------|------------------|---------------------------|-------|
| whisper small | 10 | 6 | 3 |
| ReazonSpeech | **0** | **15** | 4 |

`surface` 分類器は句点だけを見ているのではなく、**用言の終止形**も見ている（#27 の設計）。
日本語の敬体は `〜です` `〜ます` `〜ください` で終わるので、句読点が無くても
`predicate_end` が `strong_end` の役目をそのまま引き受けた。

```
predicate_end  光合成には日光と水と二酸化炭素が必要です
predicate_end  教科書の四十二ページの下の方にある図を見てください
predicate_end  この実験でいちばん大事なのは温度をきちんと管理することです
```

**#33（形態素解析器の選定）の前提が変わった。** 「ReazonSpeech を採ったから morph が必要」
という理由は消えた。#33 を進めるなら、**別の根拠**（敬体で終わらない話し言葉、体言止め、
`〜だ`/`〜である` 調）が要る。この音源にはそれらが1件も入っていない。

## 5. E2E（実サーバー / 擬似生徒10名 / 2分リプレイ / Hy-MT2）

`python scripts/replay_client.py --minutes 2 --engine hy-mt2 --asr <faster-whisper|sherpa>`。
#26 の教訓に従い**背中合わせで連続計測**した（過去の記録値と比べるとドリフトを効果と読む）。

| 指標 | whisper small | ReazonSpeech | 変化 |
|------|--------------|-------------|------|
| first caption | 5.77s | 4.17s | -28% |
| final latency 中央値 | 2.23s | 0.65s | -71% |
| final latency p95 | 3.19s | 1.75s | -45% |
| final latency 最大 | 3.61s | 1.76s | -51% |
| CPU 中央値 | 129.5% | 3.1% | -98% |
| CPU p95 | 527.0% | 442.9% | -16% |
| audio_queue_seconds p95 | 6.37s | 0.0s | -100% |
| audio_queue_seconds 最大 | 8.1s | 5.44s | -33% |
| peak RSS | 2628MB | 2592MB | -1% |
| 翻訳キャッシュ hit率 | 0.278 | 0.333 | +20% |
| 字幕カード数 | 38 | 38 | 同じ |

読み方:

- **遅延中央値 2.23s → 0.65s**。PRD N-01 の基準（中央値5s / 最大8s）に対して最大でも 1.76s。
- **CPU 中央値 129.5% → 3.1%**（論理16コア）。p95 は 527%→443% とあまり動かない — 
  これは翻訳（llama.cpp）が食っているぶんで、**ASR がCPUを占めていた時間帯が消えた**。
  実機（Core i5・論理コアが少ない）で効く可能性が高いのはこの差。
- **`audio_queue_seconds` の p95 が 6.37s → 0.00s**。#25 が有界化した音声取込の滞留が
  実質ゼロになった。#25 が置いた過負荷閾値 10秒は、ReazonSpeech 構成では遠すぎる。
  **`monitoring.overload_audio_seconds` は置き直す価値がある**（このゲートの範囲外・fog へ）。
- 翻訳キャッシュのヒット率が上がる（0.28→0.33）。ReazonSpeech の方が同じ発話を
  同じ文字列に書き起こすため、キャッシュが効きやすい。
- RSS は横ばい。モデルは 161MB で small(375MB peak) より小さいが、
  ONNX Runtime の常駐ぶんで peak RSS 単体では 508MB と大きくなる（プロセス全体では相殺）。

## 6. 負けた側・採らなかったもの

- **kotoba-whisper は落ちたまま**。CER 3.94% は ReazonSpeech(2.09%) に及ばず、
  固定費 4.717s は論外。#24 が指摘した「ゲート①は速度だけで kotoba を落とした」という
  心残りは、**精度でも速度でも勝つ選択肢が出たことで解消した**。
- **whisper small の実装は残す**（`asr.engine: faster-whisper` の1行で戻せる）。
  句読点が要る用途（記録機能の可読性など）で必要になる可能性がある。
- **hotwords は既定では無効のまま**。機構は動くが、既定の教科用語には直す対象が無い。
  実授業の誤りを見てから語彙を決める。

## 7. この数値の限界

- **音源は合成音声**（SAPI）。CER の絶対値は保証しない — エンジン間の相対比較にだけ使える。
- **開発機は Ryzen 7 8840U**。学校実機（Core i5）では固定費と限界コストの比が変わりうる。
  ただし判定は「small 比」で出ているので、順位が入れ替わるとは考えにくい。
- **句読点なしの翻訳品質は整った文でしか見ていない**。実授業の話し言葉（言い淀み・
  途中で言い直す・体言止め）では別の結果になりうる。
- **敬体で終わらない発話がこの音源に無い**。`〜だ`/`〜である` 調や体言止めが多い先生では、
  句点の消失が `surface` 分類器に効いてくる可能性が残る（#33 の判断材料）。
