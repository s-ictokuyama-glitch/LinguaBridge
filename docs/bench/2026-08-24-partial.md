# partial字幕: A/B 実測（#29）

- 機材: AMD Ryzen 7 8840U w/ Radeon 780M Graphics / 8C16T / RAM 16.4GB
- 日時: 2026-08-24
- 構成: ASR = ReazonSpeech K2 v2（sherpa-onnx・#28 の既定）/ MT = Hy-MT2-1.8B / turn = morph
- 音源: `tests/fixtures/ja/` のループ合成・2分 / 擬似生徒10名（en・zh 半々）
- 再現: `python scripts/replay_client.py --minutes 2 --students 10 --partial on|off --no-config-update`
- 生データ: [`2026-08-24-partial.json`](2026-08-24-partial.json)

**off → on → off → on を背中合わせで撮った**。#26 B-4 の教訓（単発を過去の記録値と
比べるとドリフトを効果と読む）に従い、同じ時間帯・同じ機材で交互に測っている。

数値は合成音声・開発機のもの。**条件間の相対比較にだけ使う。**

## 判定: **既定 OFF のまま出荷する**（実装・設定・テストは残す）

`partial.enabled: true` の1行で入る。生徒の「発話中」インジケーターは
**独立した設定にして既定 ON** にした（ASR を1回も増やさないため）。

チケットの合意は「CPUコストと UX 改善の両方を実測し、割に合わなければ既定OFFで出荷する」。
実測の結論は **「効くが、この機材でも +0.53コアを恒常的に払う」**。
先生が読める時間は中央値 0.53 秒早まるだけで、しかも先生は**自分が今話した内容**を
見ているので、0.5秒の先出しが判断を変える場面が想像しにくい。
生徒に届く字幕は1ミリも変わらない（partial は生徒に送らないので当然）。

学校実機（Core i5）は未計測で、p95 で既に 5.3 コアを使っている構成に
9.5% を積む判断は実機の数字を見てからにする。

## 1. 確定字幕への影響（＝入れてよいかの前提）

| 指標 | off (r1/r2) | on (r1/r2) | 判定 |
|------|------------|-----------|------|
| caption 数 | 38 / 38 | 38 / 38 | 変化なし |
| **遅延 中央値** | 1.67 / 1.76 s | 1.73 / 1.74 s | **変化なし**（off 同士が 0.09s 振れる範囲内） |
| 遅延 p95 | 3.36 / 3.26 s | 3.06 / 3.14 s | 変化なし（むしろ僅かに良い） |
| `audio_queue_seconds` 最大 | 8.06 / 8.06 s | 8.10 / 8.10 s | 変化なし |
| 過負荷サンプル | 0 / 0 | 0 / 0 | 発生せず |
| RSS 増分 | 38 / 39 MB | 41 / 41 MB | +2〜3MB |

**partial は確定字幕を遅らせていない。** これは偶然ではなく、
「ASR待ちが完全に空のときだけ interim を積む」という投入規則の結果
（`server/pipeline.py: _enqueue_interim`）。ASR は単一スレッドなので、
この規則が無ければ interim が確定 Segment の前に入って確定字幕が丸ごと遅れる。

## 2. partial の効き（UX 改善の実測）

| 指標 | r1-on | r2-on |
|------|-------|-------|
| turn 数 | 18 | 18 |
| **partial が先行した turn** | **18 / 18 (100%)** | **18 / 18 (100%)** |
| partial 送出数 | 28 | 28 |
| turn あたりの revision | 1.47 | 1.47 |
| **先出し 中央値** | **0.539 s** | **0.531 s** |
| 先出し 最小 | 0.390 s | 0.406 s |
| **先出し 最大** | **4.407 s** | **4.485 s** |
| 最後の partial が確定文と完全一致 | **94.4%** | **94.4%** |
| 不一致率（CER・確定文を参照） | 0.89% | 0.89% |

読み方:

- **どの turn にも必ず partial が先行した**（100%）。取りこぼしはゼロ。
- **先出しは中央値 0.53 秒**。全 turn が最低 0.39 秒は早い。
- **最大 4.4 秒**。これは morph が複数 Segment を連結した長い turn で、
  確定を待つと `force_silence_ms`(1000ms) と後続 Segment の ASR を丸ごと待たされる。
  **partial の価値はここに集中している**（中央値ではなく分布の裾）。
- **94.4% は最後の partial が確定文と1文字も違わない**。読み直し・書き換えの
  代償がほぼ無いということで、#21 が懸念した「partial が信用できない」は起きなかった。

## 3. 代償（CPU）

| 指標 | off (r1/r2) | on (r1/r2) | 差 |
|------|------------|-----------|-----|
| **CPU 中央値** | 9.5 / 4.2 % | 58.8 / 61.0 % | **+0.53 コア相当** |
| CPU p95 | 481.6 / 488.0 % | 533.1 / 528.2 % | **+9.5%** |
| CPU 最大 | 503.2 / 563.9 % | 591.1 / 607.6 % | +12% |

（16論理コアなので 100% = 1コア。）

- **中央値が 8.8 倍**になったのが本質。発話の合間はほぼ待ち時間で、
  off ではそこが空いている。partial はその空きを息継ぎごとに埋める。
- ただし**絶対量は 0.53 コア**で、ピーク（Hy-MT2 が回っている区間）は +9.5%。
  つまり「山を高くする」より「谷を埋める」効果の方が大きい。
- 28 件の partial は **ASR 呼び出しをおよそ 2.3 倍**にしている
  （確定 Segment 22 回 + interim 28 回）。#28 で固定費が 1.088s → 0.027s に
  なっていなければ、この回数は成立しなかった。

## 4. 想定外の収穫

**1. `interim_silence_ms=96` の interim の多くは「確定の直前」で価値が薄い。**
96ms の無音の大半はそのまま `check_silence_ms`(500ms) に達して Segment が閉じる。
価値が出るのは **[96, 500) ms に収まる文中の間だけ**で、この音源では
SAPI が読点に入れる 330〜660ms の間（#22）がそれに当たる。
turn あたり 1.47 revision という数字は「1発話につき文中の間が平均 0.47 回」を
表していて、**partial の回数は発話のリズムがそのまま決めている**
（タイマー駆動ならこうはならない）。実授業では読点の打ち方が変わるので、
この 1.47 も先出し 0.53s も変わる。

**2. 先出し量の分布は極端に偏っている（0.39s 〜 4.49s）。**
中央値 0.53s だけを見ると「効果が小さい」に見えるが、
最大は 4.4 秒で、8倍以上の開きがある。長い連結 turn では大きく効き、
単一 Segment の turn では `check_silence_ms` ぶんしか稼げない。
**もし採用するなら、効いているのは「長く話したとき」だけだと理解しておくこと。**

**3. `audio_queue_seconds` の p95 が周回ごとに 0.00 と 4.22 を行き来した。**
partial の有無と相関していない（r1-off と r2-on が 4.22、r1-on と r2-off が 0.00）。
60サンプル中1〜2回だけ 4.22 が出る形で、2秒間隔のサンプリングが
長い1発話の処理中をたまたま拾ったかどうかで決まっている。
**この指標は #25 の指摘どおり「滞留」だけを表していない**ので、
#30 で先生に出すときは「待ち」と「処理中」を分けないと同じ誤読をさせる。

**4. 翻訳キャッシュのヒット率は 4周とも 0.333 で完全に同一だった。**
partial が翻訳経路に1ミリも漏れていないことの、テストとは独立した裏付けになっている
（漏れていればキャッシュの母数が変わる）。

## この数値の限界

- 音源は合成音声。**息継ぎの分布が実授業と違う**ので、partial の回数（＝CPU）も
  先出し量も実授業では変わる。SAPI は読点で規則的に止まるが、人間は止まらない。
- 開発機は Ryzen 7 8840U / 16論理コア。**学校実機（Core i5）では 0.53 コアの
  意味が変わる**。#26 B-6 で分かったとおり、空いた CPU は llama.cpp が食うので、
  コア数が減ったときに ASR と MT のどちらが先に苦しくなるかは実機でしか分からない。
- 先生UIの体感（0.5秒早く出ることが実際に役に立つか）は数値では決まらない。
  実地検証（#19）で先生に見てもらうのが本来の判定。
