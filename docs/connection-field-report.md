# 社内の実端末での接続診断・報告票（#37）

仕様: [Issue #37](https://github.com/s-ictokuyama-glitch/LinguaBridge/issues/37)。
診断コマンドと段階別の復旧操作は [#36 の接続診断手順](connection-diagnostics.md)を使用します。
このファイルは現地担当者がコピーして埋める報告票です。空欄や未実施は成功の証拠ではありません。

**現在の状態: 現地確認待ち。** 実端末のURL・時刻・エラー・対応ログは未採取です。
最初の失敗段階、原因、制約内での復旧可否は未確定です。報告票の整備を接続復旧の成功や Issue の完了と扱いません。

## 実施条件と担当

- 既存の社内Wi-FiでサーバーPCへ直接接続します。変更対象はアプリとサーバーPCまでです。
- 社内ネットワーク変更、代替接続、別端末への証明書・追加ツール導入、ポリシー変更は行いません。
- 現地担当者が端末操作・既存設定の読み取り・時刻を限定した観測を実施し、エージェントが採取済み証拠の対応付けと報告を担当します。
- 参加コード、秘密鍵、授業の音声・字幕は添付しません。URL・画像・ログの参加コードは伏せ、IPやFW情報を含む原本は担当者間で管理します。

## 当日の進め方

1. 起動ウィンドウを残し、起動と同じ設定で `start.bat --diagnose` を実行します。カスタム設定なら #36 の Python 入口に同じ設定を渡し、JSONも保存します。診断の採用IPを実Wi-FiのIPv4と照合します。ループバックや他アダプターのIPを別端末の宛先にしません。
2. 下のサーバー比較表を埋めます。診断の採用IPが実Wi-Fi IPと異なる場合は、両方を区別して記録し、実Wi-Fi IPでも確認します。診断終了コード0は到達成功を意味しません。
3. 下の6行について、担当者が1件ずつ試行します。各試行の開始・終了時刻を記録し、同時間帯のサーバーログを保存します。別端末の `/healthz`、必要なHTTPS、実際の役割ページ、WS参加・接続を順に確認します。先に失敗した段階から後ろは無理に試さず「上流の失敗で未観測」と記録します。
4. 生徒の参加状態は先生画面の人数と照合します。先生側は画面の接続状態と同時刻のWSログを照合します。ページ表示だけではWS成功としません。接続後の通常終了・再接続を試せる場合は、その時刻・画面・終了コード・例外を記録します。到達前の切断と、接続後の終了例外を混同しません。
5. 各試行の最後の成功と最初の失敗を特定し、原因一覧と結論を埋めます。ログだけで判定できなければ、次節の追加観測を依頼し「現地確認待ち」を維持します。

## 証拠不足時の追加観測

別端末はブラウザの表示と時刻の記録だけで参加でき、開発者ツールや追加アプリを必須にしません。
まずサーバーPCで既存の待受PID・アドレス・実Wi-Fi IP・FW適用プロファイルと受信規則の条件を読み取ります。
規則が存在することは実効許可を証明せず、規則が見つからないことも遮断の証明ではありません。

それでも不明なら、担当者へ「試行ID、送信元端末、宛先IP、HTTP/HTTPSの対象ポート、開始・終了時刻（TZ付き）」を渡し、
その範囲だけ既存のサーバーPCの通信観測機能や参照可能な既存ログで、到着・拒否・応答の有無を確認してもらいます。
使用した観測方法、観測場所、権限や取得範囲の限界も記録します。取得できなければ未確認のままにします。
ping失敗、タイムアウト、アクセスログ不在、サーバーPCだけ成功という事実だけでは、FWや社内経路の遮断箇所を断定しません。

## 原因一覧

端末・ブラウザ・役割ごとに判定が異なる場合は行を分けます。
判定は「確認された問題」「非該当」「上流の失敗で未観測」「未確認」のいずれかです。
「非該当」には、その試行で除外できる証拠、または機能未使用の理由が必要です。
「上流の失敗で未観測」には失敗した上流段階を記します。未実施を非該当と扱いません。

| 対象 | 試行ID | 判定 | 根拠（証拠・時刻）/ 未観測の理由 | 最初の対処・再診断 |
|---|---|---|---|---|
| 接続先（スキーム・IP・ポート・パス・待受） | 未採取 | 未確認 | 現地未実施 | 実URLとS1/S2を照合 |
| サーバーPCのFW | 未採取 | 未確認 | 現地未実施 | 適用条件と限定観測を照合 |
| 社内経路 | 未採取 | 未確認 | 現地未実施 | 遮断箇所の根拠を採取 |
| TLS（提供証明書・端末での信頼） | 未採取 | 未確認 | 現地未実施 | HTTPS実応答と警告を照合 |
| WS | 未採取 | 未確認 | 現地未実施 | ページ到達後に参加/接続を確認 |
| 接続終了例外 | 未採取 | 未確認 | 現地未実施 | 接続後の終了とログを照合 |

| 対処後の再診断手順・対象試行ID・予定 | 未定 |
| 上流修正後に確認する後段 | 現地採取後に特定 |
| 接続復旧の状態と証拠 | 未確認（復旧成功ではない） |

最初の対処可能な原因と再診断手順が特定できたら、後段の全原因確定を待たず次の対処へ進めます。
対処後は同じ設定で #36 の診断を再実行し、S1/S2と影響した端末・ブラウザ・役割の試行を新しいIDで繰り返します。
上流が通ったら未観測だったTLS・ページ・WS・終了処理へ進み、変更内容と前後の証拠を結び付けます。

変更不可の社内経路が必要な直接接続を遮断していると確認できた場合は、
対象経路・ポート・時刻、遮断を示す観測または担当者の既存設定確認、サーバーPC側の切り分け根拠を添えて
「制約内では実現不可」と報告します。代替接続で成功扱いにしません。
端末の信頼やポリシー制約も、アプリとサーバーPCで対処できる根拠がなければ対処可能と断定しません。
根拠不足では「現地確認待ち / 復旧可否未確定」を維持します。
報告完成と接続復旧は別々に記録し、復旧成功は対象の実端末・役割での再試行証拠によって判断します。
