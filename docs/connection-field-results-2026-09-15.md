# 現地接続診断結果（Issue #37）

診断報告完成。現地担当者の端末操作とサーバー側の観測を照合し、最初に修正する対象と再診断手順を特定した。4試行の実際の接続先URLも担当者に確認済み。
接続先の手入力と許可された証明書警告の承認により、Chromebook Chrome／iPhone Chromeの生徒参加・先生接続まで進められた。
自動接続先選択・証明書の問題は未修正であり、警告なしの接続や授業機能全体の復旧を証明した報告ではない。

仕様: https://github.com/s-ictokuyama-glitch/LinguaBridge/issues/37

## 範囲と証拠

- 現地担当者が既存の社内Wi-FiでChromebookとiPhoneを操作し、エージェントがサーバー診断・ログ照合を実施した。
- 変更対象の制約は維持。社内ネットワーク変更、代替接続、別端末への証明書・追加ツール導入、ポリシー変更は行っていない。
- 証明書警告の承認は現地ルールで認められると担当者が確認した。端末の証明書ストアへの導入とは区別する。
- **iPhone Braveは担当者の「テストは省略してよい」という明示指示により対象から除外。未実施であり、合格・非該当とはしない。**
- サーバーの設定は `config.yaml`、HTTP 8000／HTTPS 8443。診断時のアプリコミットは `260797a`。
- 原本は担当者管理の `.tmp/issue37-onsite/` に保存。`server-diagnostic.json`、`http-after-start.json`、`retest-20260915-183546.log`。必要な観測を本報告にも転記した。参加コードを含み得る起動stdoutと秘密鍵は添付しない。
- 9月15日の再試行では一時ランチャーでHTTP/HTTPSのログ出力をINFOに揃え、時刻とクエリ秘匿を付加した。アプリ処理・IP選択・TLS証明書・OS設定は変更していない。

## サーバーPCの切り分け

9月11日15:53 JSTのOS診断で、実Wi-Fiは `10.53.64.130/20`、自動採用IPは `192.168.74.1`（VMware Network Adapter VMnet8）だった。
設定ポートの待受一覧は空で、HTTPプローブはタイムアウト。サーバーを既存設定で起動し、15:54:14にループバックと実Wi-Fi IPの `/healthz` がともにHTTP 200となった。
起動前の待受不在が生じた理由は未確定だが、まずサーバー起動を確保した。

9月15日のログ付き起動後も、同じWi-Fi IPを確認し、18:36:01に以下の両方でHTTP 200と期待するアプリ応答を確認した。

- `http://127.0.0.1:8000/healthz`
- `http://10.53.64.130:8000/healthz`

設定証明書のSANは `127.0.0.1` と `192.168.1.35` で、実Wi-Fi IPを含まなかった。有効期間内・鍵の一致は確認した。
9月11日のChromebook画像では `https://10.53.64.130:8443/teacher` に `NET::ERR_CERT_AUTHORITY_INVALID` が表示された（画面時計16:13）。
これは発行元の信頼に関する実観測であり、SAN不一致とは別の問題として記録する。警告承認後の表示成功は自動信頼を証明しない。

## 原因一覧

| 対象 | 判定 | 根拠と限界 |
|---|---|---|
| 接続先 | 確認された問題 | 自動選択が実Wi-FiではなくVMware。実Wi-Fi IPの手入力で両Chromeの参加・先生接続に到達。最初の修正対象 |
| サーバーPCのFW | 試行した接続の遮断原因として非該当 | 現地端末のHTTP・HTTPSページ・WS接続が成功。個別規則の寄与や他条件は未確認 |
| 社内経路 | 試行した接続の遮断原因として非該当 | 既存Wi-Fiの直接接続で成功。変更不可の経路遮断を示す証拠はなく、実現不可とは判定しない |
| TLS | 確認された問題 | 設定証明書のSAN不一致とChromebookの発行元信頼警告。警告停止中は後段未観測だったが、許可された承認後は先生接続まで成功。iPhoneの警告有無・文言は未採取 |
| WS | 試行した参加・先生接続の障害として非該当 | 4試行のaccepted/openと画面報告。音声・字幕の授業機能全体は未検証 |
| 接続終了例外 | 未確認 | Chromebookの1人→0人は確認。対応するcloseログは取得できず、例外が起きない証明には使わない。接続後に確認対象へ到達したため「上流で未観測」とは分類しない |

18:40:14に `Invalid HTTP request received.` が4件ある。送信元・要求内容は記録されておらず原因未確定。その後のAPI・WS参加は成功しており、退出時例外と混同しない。

## 最初の対処と再診断

アプリ側のIP自動選択が実Wi-Fiを選ぶよう修正するのが最優先。正しいIPの手入力は接続確認に有効だったが、自動案内URL/QRの不具合を直したものではない。
接続先確定後、サーバーPC側の証明書を実IPに一致させる。自己署名証明書の再生成だけで端末の発行元信頼は解消しないため、現地で許可された警告承認と分けて再確認する。
実装は既存の [#38（Wi-Fi接続先とQR）](https://github.com/s-ictokuyama-glitch/LinguaBridge/issues/38)、次に [#40（先生URLと証明書）](https://github.com/s-ictokuyama-glitch/LinguaBridge/issues/40) へ引き継ぐ。
接続終了・再接続の保証は [#42](https://github.com/s-ictokuyama-glitch/LinguaBridge/issues/42)、授業機能と最終受入は [#41](https://github.com/s-ictokuyama-glitch/LinguaBridge/issues/41)・[#43](https://github.com/s-ictokuyama-glitch/LinguaBridge/issues/43) で扱う。

1. [接続診断手順](connection-diagnostics.md)を起動と同じ設定で実行し、現在の実Wi-Fi IP・待受・自動案内URL/QR・証明書SANを照合する。
2. ループバックと実Wi-Fi IPの `/healthz` を比較する。
3. 両Chromeの生徒参加・先生接続・人数増減を、試行前後の時刻と最終URLを控えてログ付きで再確認する。先生画面は同時に1つにする。
4. 接続終了例外が再発した場合、その時刻・対象端末・直前操作に限定してサーバー観測を追加する。ログなしでは原因を推定せず、その項目は現地確認待ちとする。

第一の対処可能な原因と再診断手順が揃い、4試行の実URL・成功報告・対応ログの照合も完了した。Braveの省略は担当者との合意による範囲変更として明記した。後段の全原因確定を待たないという#37の条件に従い、診断チケットを完了とする。
未採取の端末情報・終了例外は上記の限界として残す。接続成功の観測、診断報告完成、未修正の問題を分け、完全復旧とは扱わない。
