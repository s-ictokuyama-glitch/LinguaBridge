# モデルの準備停止と授業の字幕継続

音声認識・翻訳の実行中処理は、期限を超えると子プロセスごと回収される。しかし、その後に作った子プロセスがモデルの生成や準備で永久停止すると、後続の要求も同じ子を待ち続ける。この条件では、先生が話し続けても翻訳字幕は復旧しない。

この検証は [inference-startup スキル](../../.agents/skills/inference-startup/SKILL.md) から実行する。製品の状態を手書きモデルへ置き換えず、Python 3.12.10 で実際の `ProcessInferenceRunner`、子プロセス、`Pipeline` を動かす。検証結果は [基準結果](inference_startup_baseline.json) に保存する。

## 選んだ対象

既存の [lesson-endurance](lesson_endurance.md) は、50分の仮想時間入力と、認識・翻訳本体の永久停止からの復旧を確認する。[推論ハング復旧の記録](inference_recovery_run.md) は、モデル準備自体の永久停止を自動復旧の対象外と明記している。

通常テスト `tests/unit/test_inference_process.py` は、遅い準備を複数の要求で共有し、最後に準備を解放すると後続要求が成功することを確認する。今回追加するのは、その待機中の操作列の列挙と、授業途中の再準備を解放しない場合の字幕継続の検査である。

本番の morph 戦略で、無音境界・推論失敗・翻訳待ちを組み合わせた有限探索も次の候補となる。今回は、再準備の停止によって以後の全字幕が失われる条件を優先した。

## 実装上の経路

`server/inference_process.py` の `_serve` は、factory と warmup を完了した後で起動応答を返す。`run` はその応答を `asyncio.shield` で待つ。要求送信前の待機中は `active` が未設定であり、要求が期限切れになってもその世代を回収しない。

この共有待機は、短い要求期限のたびに正常な重いモデル準備をやり直すことを防ぐ。一方、準備専用の期限はなく、準備が永久停止した世代を自動的に入れ替える経路もない。要求ごとのタイムアウトが守られることと、後続字幕が復旧することは別の性質となる。

ASR は音声断片ごと、MT は発話と言語ごとに要求を出す。MT の英語要求が停止した場合は、同じ発話の中国語要求が再生成を始めることもある。

## 有限探索の範囲

実際の子プロセスを factory または warmup 内で止め、最初の要求の期限切れ後に、次の逐次操作列をすべて実行する。

| 項目 | 範囲 |
|---|---|
| 操作 | `deadline` は新しい翻訳要求の正の期限を切らす。`cancel` は起動待ちへ入った要求を取り消す |
| 長さ | 0〜3。計15列 |
| 停止位置 | factory、warmup |
| 終端 | 準備を解放して翻訳、または準備を止めたままclose |
| 組合せ | 15列 × 2箇所 × 2終端 = 60ケース |

これは逐次操作列の網羅であり、同時要求やすべてのasyncio割込み順序の網羅ではない。

検査する性質は、要求の期限・取消しが共有する準備を壊さない `startup_waiter_isolation`、準備解放後の正しい翻訳 `startup_resumption`、停止時の子回収 `startup_shutdown` である。

字幕経路はASR・MT、factory・warmup、準備の解放有無を掛け合わせた8ケースを使う。`startup_recovery` は後続音声の英語・中国語字幕への到達を検査する。実 `Pipeline`、プロセス版Runner、energy VAD、simple Turn、受信記録用の接続代役を通し、推論計算だけを決定的な代役にする。

音声はID 0〜4の5件で、ID 0は障害前の正常字幕、ID 1は実行中処理の停止、ID 2は準備停止後の要求、ID 3と4は後続字幕の判定に使う。要求の期限は1秒とし、各入力の後にASR・MTの排出を待つ。継続的な実時間入力速度を測る試験ではない。

## 検証器の感度

製品コードの一時コピーにだけ、次の破壊を入れる。

| 破壊 | 検出する性質 |
|---|---|
| 起動待ちのshieldを削除 | `startup_waiter_isolation` |
| 準備後の翻訳結果を別の文字列に置換 | `startup_resumption` |
| close時の世代回収を省略 | `startup_shutdown` |

各破壊は対象の性質で失敗し、元へ戻すと正常対照が成功することを要求する。単なる例外や外側監視の期限超過は検出成功に数えない。

`startup_recovery` は現行ですでに失敗する。この測定器の感度は、一時コピーで起動待ちの世代も要求期限の回収対象にする介入を使って確認する。後続字幕が届き、元へ戻すと同じ違反が戻ることを確認する。この介入は正常な遅い準備の共有を壊すので、修正案ではない。

## 反例の読み方

永久停止ケースでは、初めに正常な音声から英語・中国語字幕を届ける。その後に認識または翻訳本体を停止させ、期限後の子プロセス回収を確認する。次の世代だけを factory または warmup 内で停止し、その先の世代は正常に動けるようにする。

停止を解除せずに後続の正常音声を入力すると、現行コードは同じ準備中の世代を保持する。後続字幕は届かない。終了時の `Pipeline.stop` と全子 PID の回収は別に判定する。

したがって現行の基準結果は `FAIL` である。既知の対象外条件を検証可能にしたもので、準備の自動復旧を実装した変更ではない。短い要求期限ごとの再生成を修正方針とみなさず、正常に遅い準備の共有も維持する必要がある。

## 実行結果

2026年11月11日、Windows、Python 3.12.10、`scripts/formal/requirements.txt` の固定依存で確認した。別のエージェントがスキルの手順から全コマンドを実行し、同じ結果を得た。基準JSONはその独立実行の出力である。

| 検査 | 結果 |
|---|---|
| 準備待ちの操作列 | 60ケースPASS |
| 準備を解放する字幕対照 | 4ケースPASS |
| 準備を解放しない字幕継続 | 4ケースとも `startup_recovery` FAIL。後続2音声の英中字幕が空 |
| Pipeline停止・子PID回収 | 全8ケース成功 |
| 実コードの破壊 | 3件を該当する性質で検出し、復元後PASS |
| 永久停止の感度対照 | 4条件で一時介入後PASS、復元後は元のFAIL |
| 既存のプロセス推論テスト | `tests/unit/test_inference_process.py` の18件成功 |

全体の終了コードは1、`status` は `FAIL`。反例を成功扱いに変えていない。

## 保証の限界

有限の操作列と実プロセスの固定ケースに限った検査であり、無制限の形式証明ではない。全 OS スケジュール、すべてのタイミング、子プロセス生成の失敗、任意のモデル内部動作は網羅しない。

音声と認識・翻訳結果は決定的な代役を使う。マイク、実 LAN、生徒画面、字幕の意味精度、記録保存、実モデルの自然発生ハング頻度は測らない。既定60秒の要求期限を待つ50分試験や、サーバーPCでの性能測定の代わりにはならない。

検証用の短い期限と外側の監視時間は、実行を有限にし子プロセスを残さないための設定である。製品の復旧時間の保証として扱わない。
