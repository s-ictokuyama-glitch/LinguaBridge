# 接続ごとの送信キューの有界検証

`client_delivery.py` は実際の `ClientSender` を操作し、遅い接続や送信失敗が他の生徒の配信を止めないことを確認する。
既存の [caption-recovery](../../.agents/skills/caption-recovery/SKILL.md) が除外する送信障害を補う。
ASR推論、記録の所属、字幕履歴からの復元はそれぞれ既存スキルの範囲に残る。

## 道具と判定

Python 3.12.10 と [固定依存](requirements.txt) を使い、有限の操作列を実コードに全列挙する。
asyncio のキュー、`wait_for`、タスクのキャンセルをそのまま実行するため、別言語の手書きモデルよりコードとの対応を確認しやすい。
SMT による証明、TLA+ モデル、無限の入力に対する形式証明ではない。

検証器の期待値は待機列、送信中のID、成功したID列、受付可能かどうかで管理する。
製品の内部キューやタスクを期待値として読み戻さない。
公開プロパティの `pending`、`alive`、`send` の戻り値、ソケットで観測した送信と切断を比較する。

| 性質 | 確認する約束 | 違反したときの影響 |
|---|---|---|
| `capacity` | 待機列が満杯なら受理せず、その接続を停止する | 遅い端末の待機列が増え続ける |
| `admission` | 停止・終了後は新しい送信を受理しない | 届かない字幕を受理済みと扱う |
| `fifo` | 送信開始と正常受信が、受理した順序と一致する | 字幕の逆転・重複・欠落が起きる |
| `retry_close` | 溢れ・送信例外・期限超過の結果で一度だけ1013切断する | 生徒が再接続による回収へ進めない |
| `drain` | 正常終了時は受理した残りを順番に送り切る | 接続終了直前の字幕が欠ける |
| `timeout` | 実際の `wait_for` 期限超過後は受付を停止する | 送信不能な接続を維持する |
| `isolation` | 遅い生徒が溢れても、正常な生徒は全件を順番に受け取る | 1台の不調で他の生徒も字幕を失う |

## 探索する操作と原子性

容量1と2それぞれについて、次の7操作の長さ0〜4の全列を試す。
候補は合計5,602列で、操作の前提が成立する461列を最後まで検証する。
未開始の送信への成功・障害注入、停止後の `dispatch` は入力範囲から除く。
合法でない列でも、それより前に検出した性質違反は結果に残す。

| 操作 | 実コードへの入力 | スケジューラーへの制御移譲 |
|---|---|---|
| `send` | 一意なseqを持つ辞書を `ClientSender.send` へ渡す | なし。連続投入でキューを埋める |
| `dispatch` | ワーカーを実行し、先頭1件のソケット送信をゲートで止める | `sleep(0)` 12回 |
| `success` | 送信中のソケットを成功させる | 同じ12回。次の送信があればゲートで止まる |
| `error` | 送信中のソケットへ `ConnectionResetError` を注入する | 同じ12回 |
| `timeout` | 送信中のソケットへ `TimeoutError` の結果を注入する | 同じ12回 |
| `close` | 正常ならソケットを順次成功させて `aclose(1秒)`、停止済みなら `aclose(0秒)` | 実際のawaitで待つ |
| `abort` | `aclose(drain_timeout_s=0)` で未送信分を諦める | 実際のawaitで待つ |

`send` は同期関数なので途中へ割込みを入れない。
12回の制御移譲はキューの取出し、`wait_for` の子タスク、切断タスクを進める固定のスケジューラーである。
全await順序を網羅する主張ではない。
ソケットのゲートは製品コードが実際に待つ送信境界に置く。
正常な列の最後は全ソケット送信を成功させ、正常排出の完全性を確認する。
切断済み・`abort` 後の残りは破棄可能とし、新規受付の拒否と観測済みの受信順を確認する。

`timeout` 操作は経過時間を再現しない。
別の `real_timeout` ケースで `send_timeout_s=0` の実際の `asyncio.wait_for` を通し、期限超過と1013切断、未配送、後続受付拒否を確認する。
これは送信開始前に期限切れになる境界であり、正の期限での実時間の経過や遅延分布は保証しない。

`isolation` は実際の `Roster` に同言語の生徒2人を登録する専用ケースである。
容量1の一方を最初の送信中に止め、4回 `broadcast` する。
各回で正常な生徒に全件届くことと切断されないことを確認し、遅い生徒だけが1013切断されることを確認する。
これは全操作列との直積ではない。

## 検出能力の確認

`--mutation-check` は `server/` と検証器の一時コピーを作り、製品コードを一箇所ずつ壊す。
各破壊に対して、まず同じ入力が元の実装で成功することを確認する。
子プロセスは期待した性質の違反と終了コード1を返す必要がある。
Traceback、30秒のタイムアウト、置換箇所の不一致は破壊の検出として数えない。

| 破壊 | 健全な入力 | 期待する違反 |
|---|---|---|
| 容量を無制限にする | `send,send,send` | `capacity` |
| FIFOをLIFOに変える | `send,send,dispatch` | `fifo` |
| 終了後も受理する | `close,send` | `admission` |
| WebSocket切断を省く | `send,send` | `retry_close` |
| 正常排出待ちを省く | `send,close` | `drain` |
| 期限超過時の停止を省く | `real_timeout` | `timeout` |
| 送信例外時の停止を省く | `send,dispatch,error` | `admission` |
| Rosterの送信キューを共有する | `isolation` | `isolation` |

たとえばLIFOへの破壊では、容量2でseq1、seq2を投入し、ワーカーを進めると、seq1ではなくseq2から送信を開始する。
元の実装へ戻すと同じ入力は成功する。
基準結果は [client_delivery_baseline.json](client_delivery_baseline.json) に保存する。

## 範囲外

本物のWebSocket、ネットワーク、ブラウザー、復元後の表示、MT失敗、同じソケットの再参加、先生の置換、同時 `aclose`、タスク外部キャンセルは調べない。
容量には待機中だけを数え、送信中1件は別枠とする既存仕様を使う。
辞書の投入後変更、任意サイズのpayload、無制限の入力、全スケジューラー順序は対象外とする。

ソケットの `close()` は完了することを仮定する。
現実装の `_kill` は期限を付けずに切断タスクを開始する。
`aclose` はそのタスクの完了を期限なしで待ち、`drain_timeout_s` はその後の `queue.join()` だけを制限する。
`close()` を止める実コード実験でも、ゲートを解放するまで `aclose()` が未完了になることを確認した。
したがって、この検証の成功をサーバー終了全体の時間上限の保証として扱わない。
