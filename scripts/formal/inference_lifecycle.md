# 推論ライフサイクルの有界検証

対象は `server/inference.py` の InferenceRunner である。非同期の待機終了と、スレッドでのモデル処理の終了を分けて扱う。待機が期限切れになっても、実行中のモデルを中断できない。次の要求は同じ実行先で順番を待つ必要がある。

これは明示的なエンジン・Executor注入で使うスレッド実行の契約である。設定から起動するASRと翻訳は `ProcessInferenceRunner` を使い、準備後の実行中の要求が期限切れになった子を回収する。その保証は [lesson-endurance](lesson_endurance.md) と `tests/unit/test_inference_process.py` で別に確認する。

## 道具と実装の対応

検証器はPython 3.12.10の標準ライブラリだけで実コードを実行する。Pythonのasyncioと concurrent.futures を含むこの処理を直接扱う、導入済みのSMT検証器は使わない。手書きの別言語モデルとのずれを避け、有限の操作列を全列挙する方法を選んだ。無制限の形式証明ではない。

`ControlledExecutor` は同時に1件だけを running とし、残りを FIFO で待たせる。標準ライブラリの Future を使い、未着手の取消しと、稼働中は取り消せない契約を保つ。処理本体の実行と結果・例外の確定は complete でまとめて行う。モデル内部の途中の副作用は表さない。

期待状態は要求ごとの worker と caller に分けて持つ。たとえば期限切れの要求でも worker は running のままで、caller は InferenceTimedOut になる。開始・完了順序と要求別の帰結を、この期待状態と比較する。

| 入力 | 実コードの動作と待機境界 |
|---|---|
| ok、error、timeout_error | run をタスクにして投入し、submit の観測まで進める。timeout=None。処理の帰結は要求ID、ValueError、TimeoutError |
| expire | timeout=0 で投入し、待機終了まで進める。すでに running の要求は残り、queued の要求は取り消される |
| finish | 実行中の Future を完了し、対応する呼出タスクと後続処理へコールバックを進める |
| cancel0、cancel1 | 指定した未完了の呼出タスクをキャンセルし、Futureへの伝播を進める |
| stop | stop を実行して、未着手要求の取消しを進める。停止後の投入も探索に含む |
| finish_cancel、cancel_finish | Future完了と呼出タスクのキャンセルを、イベントループへ制御を戻す前の両順序で行う |

run の submit は最初の await より前に実行される。取消しと Future 完了は実際の await の待機中に与える。各操作後は8周回の `asyncio.sleep(0)` で Future 接続のコールバックを処理する。操作内部に架空の割込みは追加しない。8周回で安定しなくなった場合は検証器の境界を再確認する。

## 探索の上限

既定では10操作の長さ0〜5、111,111列を候補とする。最大2要求、stop は1回とし、存在しない要求の取消しなどは不正列として除く。有効な1,850列をそれぞれ新しい runner で実行する。各列末尾では、残る稼働中要求を順番に完了し、未停止なら停止する。この後処理は長さの上限外である。

`--depth` は0〜6に変更できる。`--case` は列を1つに絞り、実スレッドケースを省く。終了コード0は指定範囲で反例なし、1は性質の違反である。実行例と結果の読み方は [inference-lifecycle スキル](../../.agents/skills/inference-lifecycle/SKILL.md) に置く。

## 既定の実スレッド

注入した単一Executorだけでは、製品の既定値が複数スレッドへ変わる退行を検出できない。別に、既定の InferenceRunner を作る4ケースを実行する。

1. 最初の要求を実スレッドで開始し、Eventで処理を保留する。
2. 最初の要求を成功待ち、期限切れ、キャンセル、停止前の成功待ちのいずれかにする。期限切れでは0.01秒を設定し、処理開始を確認してから期限切れを待つ。
3. 後続2要求を投入する。最初のゲートを保留中に0.1秒の観測区間を置き、後続の開始がないことを確認する。
4. 停止ケースでは別スレッドで stop を呼び、実行中のゲートを解放する前に2秒以内で戻ること、後続2要求が取消しになることを確認する。ほかはゲートを順に解放し、3要求の結果と要求IDを比較する。

スレッド開始の待機上限は2秒、処理ゲートの保護上限は5秒とする。上限超過は網羅的な反例ではなく、実行失敗として扱う。OSの全スケジュールの証明や性能測定ではない。実モデルの中断可能性やGPU側の並行性も検証しない。

## 破壊検出

`--mutation-check` は一時コピーの製品コードへ次の破壊を1つずつ適用する。各子プロセスは終了コード1と、指定した性質の違反を返す必要がある。例外や置換不一致は検出成功に数えない。

| 破壊 | 検出する性質 | 反例 |
|---|---|---|
| 既定スレッドを2本にする | serial_execution | 最初の処理を保留中に2件目が始まる |
| stop で queued の取消しを省く | queued_cancellation | ok,ok,stop で2件目が取消しにならない |
| キャンセルを通常の失敗に変える | caller_outcome | ok,cancel0 の呼出結果が CancelledError にならない |
| 処理自体の TimeoutError を期限切れに変える | caller_outcome | timeout_error,finish が InferenceFailed にならない |
| 同じ処理を2回投入する | execution_order | ok,finish で開始IDが重複する |
| stop を同期的な待機指定に変える | nonblocking_stop | 実行中のゲートを保留している間に stop が戻らない |

nonblocking_stop は実スレッドでの帰還の観測であり、shutdown の引数そのものは比較しない。OSによる停止スレッドの開始には2秒の待機上限を設け、開始失敗は実行失敗として扱う。開始後2秒以内の帰還を要求するため、OSがその間スレッドを止める環境では結果を再確認する。

[基準結果](inference_lifecycle_baseline.json) は同期コミット `4efcb9f6edd2b1e39aea9c173d9b8b29870861f1` の製品コードに対応する。有効列1,850、実スレッド4ケースはPASS、6破壊はすべて検出した。製品コードの反例は見つからなかった。
以前の `5aa0ca374beb563376b247eee60fd811e954e977` から PR #181 のマージ後コミットへ同期参照だけを直した履歴とは別に、今回は [全検証を再実行](maintenance_20261114.md) して同期した。

## 対象外

全await順序、全スレッド順序、3件以上の要求の全列挙、処理中の副作用、実モデル、GPU、複数runnerの独立性、ASRと翻訳の同時実行、字幕・キャッシュ・記録への反映は保証しない。正の期限と完了が同時に到来する競合や、期限を設定した処理が自ら TimeoutError を投げる場合も全列挙に含まない。成功の経過時間値は比較しない。
