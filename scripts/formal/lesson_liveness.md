# 音声入力から翻訳字幕までの継続性

`lesson-liveness` は、授業中に音声入力を繰り返しても、認識・翻訳・配信が進み続けることを調べる。
既存の `asr-backlog` と `inference-lifecycle` は個々の部品を検証する。`caption-recovery` は再接続の復元を扱い、`lesson-recording` は生徒なしで記録を調べる。
この検証は、それらの間にある `Pipeline` のASRワーカーと `CaptionDelivery` のMTワーカーを同時に実行する。
実行手順と変更時の照合先は [スキル](../../.agents/skills/lesson-liveness/SKILL.md) に記載する。

## 道具と入力の境界

Python 3.12.10による有限操作列の全列挙を使う。独立した手書きモデルでは、asyncioのキュー、Future、Eventを製品と二重管理するため、実コードを動かす方式を選んだ。
SMT検証、全状態のモデル検査、無制限の形式証明ではない。
依存は [requirements.txt](requirements.txt) のnumpy 2.5.4、pydantic 2.13.5、PyYAML 6.0.3に固定する。

```text
PCM16 → Pipeline.feed_audio → VoiceSegmenter → AsrBacklog
      → InferenceRunner → TurnAssembler → CaptionDelivery
      → InferenceRunner → Roster → ClientSender → 記録用Socket
```

音声は16kHz、100msの定数波形と100msの無音を組にする。非ゼロ振幅 `1000 + 入力ID` で各入力を区別する。
EnergyVADの閾値は300、確定無音は100ms、pre-rollは0、Turnはsimple、途中認識は無効とする。
ASRの計算だけを「授業の発話IDです。」へ、MTの計算だけを「言語:原文」へ置き換える。
キュー、ワーカー、例外分類、採番、キャッシュ、送信処理は製品実装を使う。
先生1人と英語・中国語の生徒各1人を接続し、Socketの送信は即座に完了する。

標準ライブラリの `Future` を使う制御用Executorは、先頭の仕事だけをrunningにする。
操作間でイベントループを16周回進める。これは明示したスケジューリング境界であり、実行時間や任意のasyncio順序の保証ではない。
warmupは即時に成功させ、統計送信周期は3600秒にする。

## 全列挙する範囲

5操作の長さ0〜6を列挙する。合計19,531列のうち、完了対象が存在する413列を検査する。

| 操作 | 実コードへの作用 |
|---|---|
| `feed` | 次の固有IDのPCMと無音を `feed_audio` へ渡す |
| `asr_ok` | 実行中ASRのFutureへ計算結果を返す |
| `mt_ok` | 実行中MTのFutureへ計算結果を返す |
| `asr_fail` | 実行中ASRのFutureへRuntimeErrorを返す |
| `mt_fail` | 実行中MTのFutureへRuntimeErrorを返す |

MTキュー容量1、復元水位1、字幕履歴3、翻訳キャッシュ2とする。ASR容量と送信容量は既定値を使う。
実行中の仕事がない完了操作は不成立とする。最大6音声を投入し、列の末尾で残った推論を順に正常完了させる。
排出後にもう1音声を投入し、続けて字幕まで届くことを確認する。
各列ではASR容量を超えない。容量を超えた音声の受理規則は `asr-backlog` の担当範囲である。

期待する先生の字幕は投入IDから採番し、注入したASR失敗だけを除く。
生徒の期待値も投入IDから原文・訳文・言語・seqを作り、注入したMT失敗だけを除く。
製品が実際に返した件数や訳文を、そのまま正解として使わない。

`finish` は実際の `Pipeline.drain` を起動し、残ったFutureをASR、MTの順に解放する。
最大 `4 × (投入数 + 4)` 周期の制御用ループで排出を待つ。各周期でコールバックを進め、解放した推論の後でも同じ処理を行う。
drainの早期完了、完了しない排出、ワーカー終了、内容・順序・件数の不一致、正常接続の切断を検出する。
5秒の列監視と30秒の固定ケース監視は検証器の停止防止であり、製品の遅延基準ではない。

## 長い固定ケース

以下は固定した順序の観測であり、601入力の全実行順序を列挙した結果ではない。

| ケース | 入力と期待する結果 |
|---|---|
| `distinct` | 固有音声600件を順に排出し、最後に追加1件。ASR601回、MT1202回、各生徒601字幕。16/17、履歴50/51、キャッシュ512件の境界を越える |
| `repeated` | 同一音声64件と新しい音声1件。各生徒65字幕、MT4回、キャッシュhit126回。キャッシュで推論を省いても採番・配信を続ける |
| `capacity` | 最初のMTを保留し、140音声を投入。MTキューが既定容量256になった事実と先生への過負荷通知を確認してから解放する。追加1件も含め各生徒141字幕 |
| `asr_timeout` | timeout=0でASR待機を終了。running Futureが残ることと通知を確認し、Futureを完了させる。期限を60秒へ戻して次の音声を処理する |
| `mt_timeout` | timeout=0でMT待機を終了。両言語の当該字幕を失敗扱いとし、残ったnative Futureを完了後、次の音声を両言語へ届ける |
| `held_drain` | MTを保留した状態でdrainを呼び、MTが残ったまま帰還しないことを確認してから追加音声を処理する |

最初の3ケースはAppConfigの既定値である履歴50、MT容量256、キャッシュ512を使う。
ASRの容量は30秒、送信容量は64件である。`capacity` は短いPCMを使い、ASRの容量超過を起こさずMTの背圧を検査する。
一時的なASR・MT失敗の組合せは全列挙側で扱う。

## 破壊が検出できること

`--mutation-check` は `server/` を一時ディレクトリへコピーし、同じ検証器を別プロセスで実行する。
各ケースの通常版が成功し、破壊版が狙った性質で失敗することを要求する。
Tracebackや子プロセスの期限超過を「検出成功」に数えない。

| 一時コピーの破壊 | 検出する性質 |
|---|---|
| ASRワーカーを16件処理後に終了する | `worker_liveness` |
| MT投入後の起床通知を消す | `eventual_drain` |
| 満杯のライブMTジョブを捨てる | `caption_delivery` |
| MTの排出を待たずにdrainを返す | `drain_completion` |
| 配信する訳文を別の文に置き換える | `caption_delivery` |
| 確定した日本語を別の文に置き換える | `recognition_delivery` |

たとえば「16件後に終了」の反例は、16件目の音声認識を完了した直後にASRワーカーが終了する。
「MT起床通知なし」の反例は、音声を認識して翻訳を積んでもMTが始まらず、排出を完了できない。
各反例は `trace` と最初の不一致を出力する。全列挙では長さ順に探索し、性質ごとの最初の反例を保持する。
固定ケースのtraceは最短化しない。

## 実モデルと画面の別検査

`lesson_liveness_real.py` は `create_app` の未注入経路と `config.yaml` の実モデル・VAD・Turnを使う。同じPipelineの翻訳キャッシュだけを無効にし、既定では32回、同じ音源を投入する。開始時に両モデルの子PIDの生存を確認し、停止後に両PIDが消滅してからPASSとする。
各回は100ms単位のPCM、1.2秒の無音、flush、drain、送信キュー排出の順で処理する。
各回の先生の認識結果に対応する非空の訳文が両生徒へ届くこと、通算seqの連続性、ASR破棄0、キュー残留0、MT呼出数を調べる。
`--models-dir`、`--wav`、`--repeats` で条件を指定でき、`--repeats` は17以上を要求する。
出力には設定、依存版、音源のSHA-256、モデルファイル情報と各回の内容が残る。認識・翻訳の品質を採点するものではない。

`lesson_liveness_view.py` は記録されたSocketのフレームを、Playwright 1.64.1と実ブラウザーのWebSocket受信イベントへ再生する。
生徒ページのHTML、`student.js`、`caption-recovery.js` をそのまま読み、全カードのseq・原文・訳文・言語・順序を期待値と比較する。字幕領域と最新の訳文が非表示でないことも確認する。
最後に授業終了フレームを送って、その受信まで待ってからDOMを読む。
形式検証の期待値は投入IDに由来する。実モデルの表示検査の期待値はサーバーから届いた字幕に由来し、画面への反映だけを検査する。
画面の破壊検査は `student.js` の一時コピーで17件目以降を無視させ、32件以上を期待する検査が16件しか表示されないことを検出する。17件目から字幕領域を隠す破壊も、`caption_visibility` 違反で検出する。
Edgeがない環境では、対応ブラウザーを用意して `--channel chromium` などを指定する。

## 結果と保証の限界

同期コミットは `5aa0ca374beb563376b247eee60fd811e954e977`。基準結果は [lesson_liveness_baseline.json](lesson_liveness_baseline.json) に保存する。
このコミットでは成立413列、固定6ケース、製品コピーの6破壊検出が成功した。現行コードの性質違反は検出されなかった。
601入力を含む全固定ケースの生徒画面も一致し、16件後の表示停止と非表示化を検出した。
既定のHaas int8・Hy-MT2・Silero・morphで音源03.wavを32回処理し、ASR32回、MT64回、英中各32字幕を確認した。
同じ32回の字幕を生徒ページへ再生し、16・17・32件目を含むDOM内容と最新字幕の可視性を確認した。
基準結果には実モデルの設定・依存版・音源ハッシュと、1・16・17・32回目の内容を含める。
現行コードの違反が見つかった場合は結果を保持し、前提や期待値を弱めて成功へ変えない。

各推論が最終的には返ることと、正常な接続へ送れることが継続性の前提である。
この検査に注入する `InferenceRunner` のtimeoutは待機を打ち切るだけであり、永久に戻らないnative処理を中断する機能はない。
同じ単一Executorに残った処理が永久停止した場合の回復は、この検査では保証しない。
設定から起動する製品の `ProcessInferenceRunner` は、モデル準備後の実行中の要求が期限切れになった子を回収して後続要求を再開する。その検証は [lesson-endurance](lesson_endurance.md) と [実行記録](inference_recovery_run.md) を参照する。

マイクからの収音、実WebSocket・LAN、同時の先生操作、再接続、途中字幕、録音保存、実モデルの精度、50分授業、持続的な過負荷時の処理速度、メモリー増加は対象外である。
実モデル32回は、各回の完了を待って次を入れる有限観測であり、授業中の音声到着速度に追いつくことの証拠には使えない。
